## Key architecture observations

* Rendering pipeline centralized in `mcp_core.core.diagram_rendering` / `diagram_service`
* Config single source: `mcp_core.core.config.MCPSettings`, env-driven
* FastMCP wrapper `mcp_core.server.fastmcp_wrapper` provides mock fallback for testing
* Diagram catalog in `tools.kroki.kroki.LANGUAGE_OUTPUT_SUPPORT`
* Cache hint exposed via `get_mcp_cache_policy` → cache_ttl 300, cache_scope public – no real render cache, `cache_hit` flag currently informational
* Batch generation processes items sequentially, no bounded concurrency
* HTTP client reuse not centralized; Kroki client created per call
* No Origin/Host validation for HTTP MCP, CORS is permissive
* File output uses `MCP_OUTPUT_ROOT` concept but no enforced sandbox check
* Rate limiting is in-process per-IP only
* No OpenTelemetry instrumentation
* Validation diagnostics are strings, no structured `ValidationDiagnostic`

## Security / safety

* Output path resolves to `output_dir`; no explicit path traversal guard documented
* CORS allows credentials with wildcard risk
* No MCP Origin validation
* No request/response size limits enforced
* No secret redaction guarantees in logs
