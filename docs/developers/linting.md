# `uml-mcp lint`

LLMs choose and call tools from their descriptions, annotations and schemas.
Weak metadata leads to wrong tool choices, and a wrong `readOnlyHint` gives the wrong
auth scope. `uml-mcp lint` catches both, plus risky configuration, before
deployment. The rules are inspired by [MXCP's linter](https://mxcp.dev/quality/linting/).

```bash
uv run uml-mcp lint                                   # in process; exit 1 on errors
uv run uml-mcp lint --strict --min-grade A --token-budget 5500   # the CI gate
uv run uml-mcp lint https://mcp.contoso.com/mcp       # any running server (MCP_LINT_TOKEN for auth)
uv run uml-mcp lint --format json | jq .grade
uv run uml-mcp lint --quiet && echo passed
```

Exit codes follow `mcpx`: `0` passed, `1` failed (errors, `--fail-on warnings`/`--strict`,
grade below `--min-grade`, or over `--token-budget`), `2` server unreachable.

It runs two layers:

1. **Protocol rules.** It connects like a client (`initialize`, `tools/list`,
   `resources/list`, `prompts/list`) and applies the
   [MCP Playground grading](https://www.mcpplayground.tech/docs/grading) rules
   used by `mcpx`. It prints a score out of 100 (error −15, warning −5, info −1),
   a grade (A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60, else F), and a token estimate
   (about 4 characters per token over everything a client loads on connect).
2. **Definition and config rules.** These are MXCP-style checks the wire can't see,
   such as docstring `Args:`, annotations and risky configuration.

CI runs the gate above in the `lint` job. The same results appear in the
admin dashboard's **Lint** tab and at `GET /admin/api/lint`.

## Protocol rules (mcpx-compatible)

| Rule | Severity | Check |
| --- | --- | --- |
| `tool-no-description` | error | Tool has a description |
| `tool-short-description` / `tool-long-description` | warning | 10–500 characters (aim for < 300) |
| `tool-description-is-name` | warning | Description is more than the name |
| `tool-no-schema` / `tool-schema-not-object` | warning / info | `inputSchema` present and of type object |
| `prop-no-description` / `prop-no-type` | warning | Every parameter has a description and a type (`type`, `anyOf`, `$ref`, `enum`, …) |
| `tool-no-required` / `tool-empty-schema` | info | Required parameters declared / tool takes arguments |
| `required-not-in-properties` | error | Every required field exists |
| `tool-name-convention` | info | snake_case or kebab-case |
| `resource-no-name` / `resource-no-description` / `resource-no-mimetype` | warning / warning / info | Resource metadata |
| `prompt-no-description` / `prompt-arg-no-description` | error / warning | Prompt metadata |
| `server-empty` / `server-duplicate-tools` | error | Server exposes something; tool names unique |
| `server-no-name` / `server-no-version` | warning | `initialize` returns name and version |

## Definition and config rules

| Code | Severity | Target | Check |
| --- | --- | --- | --- |
| TOOL002 | warning | tool | Description is at least 40 characters (what it does, when to use it, what it returns) |
| TOOL003 | warning | tool | `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` are set (read/write auth is derived from `readOnlyHint`) |
| TOOL004 | info | tool | `annotations.title` is set |
| TOOL005 | warning | tool | Declares an `output_schema` |
| TOOL006 | warning | tool | Every parameter has a type annotation |
| TOOL007 | warning | tool | Every parameter is described under `Args:` in the docstring |
| TOOL008 | info | tool | Has a usage example |
| CFG000 | error | auth | Enterprise auth configuration fails to load |
| CFG001 | warning | auth | `resource_url` is not HTTPS |
| CFG002 | warning | audit | Auth is on but the audit trail is off |
| CFG003 | warning | rate_limit | Auth is on but rate limiting is off |
| CFG004 | warning | audit | `include_inputs: full` may store sensitive diagram content |
| CFG005 | error | audit | `file` sink without `audit.file` |
| CFG006 | info | admin | `allow_local_without_auth` is ignored while auth is on |
| CFG007 / CFG008 | error | tools / rate_limit.tools | Unknown tool name (typo would silently do nothing) |
| CFG009 | info | tools | Tool disabled by configuration |
| AUTH001 | warning | tool | No `readOnlyHint` and no `tool_permissions` entry, so it defaults to write |

## Token footprint

Every client pays for `tools/list` on connect. Output schemas generated by Pydantic
are compacted losslessly at registration
(`mcp_core/tools/tool_decorator.py::compact_schema`: no auto `title`, no
`"default": null`, `type: [X, "null"]` instead of `anyOf`). This cut the footprint
from about 6,460 to about 5,050 tokens at the same grade.

## Local cross-checks (not in CI)

External tools give a second opinion. They need network access, so they run
locally only:

```bash
npx @samsec/mcpx lint https://uml-mcp.vercel.app/mcp --min-grade B --token-budget 6000
mcp-tester conformance http://127.0.0.1:8000/mcp     # cargo install mcp-tester
mcp-tester tools http://127.0.0.1:8000/mcp
```

## Adding a tool

`tests/test_lint.py::test_real_registry_is_strict_clean` fails when a new tool,
prompt or resource introduces an error or warning. Fix the definition rather than
relaxing the test. The fix is usually a longer description, the four annotations,
an `output_schema`, or an `Args:` entry.
