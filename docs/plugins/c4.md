# C4 model plugin

`uml-mcp-plugin-c4` adds one diagram type, `c4_model`: a single JSON model that covers the
three C4 levels, from people and software systems down to the components inside a container.

| Output | What you get |
| --- | --- |
| `svg` | The starting view in C4 notation, with a legend |
| `html` | A standalone page that opens on the starting view and drills down from there |

It ships with uml-mcp and is on by default (`plugins.bundled`). The page runs locally with no
CDN or network access, in the sandboxed plugin frame, under a hash-based CSP. The Kroki
`c4plantuml` type is unchanged; use it when you want PlantUML's C4 macros or a deployment view.

## Source format

| Field | Notes |
| --- | --- |
| `title`, `description` | Shown above the context view |
| `theme` | `dark` (default), `light` or `auto` (static output is dark; the page follows the reader's system) |
| `direction` | `auto` (default), `TB` (top to bottom) or `LR` (left to right). With `auto` the SVG takes the flow closer to a landscape page and the HTML page shows whichever one is larger in its frame |
| `people[]` | `id`, `name`, `description`, `external` |
| `systems[]` | `id`, `name`, `description`, `external`, `containers[]` |
| `systems[].containers[]` | `id`, `name`, `technology`, `description`, `kind`, `service`, `docs`, `components[]` |
| `containers[].components[]` | `id`, `name`, `technology`, `description`, `service`, `docs` |
| `relations[]` | `from`, `to` (any element ids), `label`, `technology`, `async` |
| `view` | `level` (`context`, `container`, `component`) and `focus` (a system id for `container`, a container id for `component`): the view the SVG draws and the page opens on |

`kind` sets the container's shape: `app` (a box, the default), `web` (a browser window),
`db` (a cylinder), `queue` (a pipe on its side), `storage` (a bucket) or `function` (a
hexagon). `service` names what the container runs on, such as `aws:lambda`, `gcp:run` or
`postgres`, and gives its detail card an **Open documentation** button: the vendor's official
docs, from the same map the [D3 plugin](d3.md) uses. `docs` overrides it with your own
`https://` page.

Ids are unique across the whole model, so a relation can name any element at any level.
Validation reports every problem at once, each with the field it is about:

```text
relations[3].to 'paymnts' is not a known element; known ids: customer, shop, web, api, ...
view.focus 'api' is a container; the container level needs a system id
relations[5] connects 'api' to 'shop', which contains it; relate elements to their siblings or to other elements instead
```

Limits: 300 elements (`plugins.settings.c4.max_elements` can lower it) and 600 relations.

## Levels and lifted relations

| View | Boxes | Inside the dashed boundary |
| --- | --- | --- |
| Context | Every person and software system | Nothing |
| Container (`focus` a system) | The people and systems the containers talk to | The system's containers |
| Component (`focus` a container) | The people, systems and sibling containers the components talk to | The container's components |

A relation is drawn at the level on screen: each end is replaced by its nearest visible
ancestor. A call from one component to a component in another container shows as a line
between the two containers in the container view, and as a line between the two systems in the
context view when they are in different systems. Relations that land on the same pair of boxes
are merged into one line whose label lists them all. A relation to the opened element itself
(a person who uses the whole system) ends on its boundary.

## The page

| Action | Result |
| --- | --- |
| Click a system or container with a ⊕ mark | Zoom into its containers or components |
| Click any other box, or Shift+click | Its detail card: description, technology, relations in and out, Open documentation |
| Click a line | The relations it stands for |
| Breadcrumbs, ↑ or Esc | Back up one level |
| Drag, wheel, `+`, `-`, `0`, Fit | Pan, zoom, reset |
| Theme | Light or dark |
| Export | SVG, PNG or a static HTML page of the level on screen |

A relation in a detail card jumps to the other element, switching level when it lives in
another view. Each view opens fitted to its frame; inside the MCP App viewer the page drops its
own title, links open through the host, and the viewer's export buttons reach the page's.

## Example

The internet banking system below is the plugin's example (`uml://examples`): two people, the
banking system with six containers, the API application with five components, and two
external systems.

```json
{
  "title": "Internet banking system",
  "people": [{"id": "customer", "name": "Personal Banking Customer"}],
  "systems": [
    {
      "id": "banking",
      "name": "Internet Banking System",
      "containers": [
        {"id": "spa", "name": "Single-Page App", "technology": "React", "kind": "web"},
        {
          "id": "api",
          "name": "API Application",
          "technology": "Java and Spring Boot",
          "components": [
            {"id": "signin", "name": "Sign In Controller", "technology": "Spring MVC"},
            {"id": "security", "name": "Security Component", "technology": "Spring Bean"}
          ]
        },
        {"id": "db", "name": "Database", "technology": "PostgreSQL", "kind": "db", "service": "postgres"}
      ]
    },
    {"id": "mainframe", "name": "Mainframe Banking System", "external": true}
  ],
  "relations": [
    {"from": "customer", "to": "spa", "label": "Views balances"},
    {"from": "spa", "to": "signin", "label": "Signs in", "technology": "JSON/HTTPS"},
    {"from": "signin", "to": "security", "label": "Uses"},
    {"from": "security", "to": "db", "label": "Reads and writes", "technology": "JDBC"},
    {"from": "api", "to": "mainframe", "label": "Reads accounts", "technology": "XML/HTTPS"}
  ],
  "view": {"level": "container", "focus": "banking"}
}
```

```bash
uml-mcp plugins enable c4   # only needed with plugins.bundled: false
```
